    Práctica 2 — No equipo anfitrión (GPU)

    Práctica 2 — Ollama no equipo anfitrión (con GPU)

    Automatización (apéndice)

    Ver Apéndice · Ollama · host con GPU.

    Esta práctica describe a alternativa con máis potencia: instalar Ollama no teu equipo anfitrión (aproveitando a GPU) e usar unha VM de Kali —como a xerada na Práctica 1 (Ollama dentro dunha VM)— como simple cliente por rede.

    Instalación

    Antes de instalar: comproba a túa GPU (se tes)

    Ollama acelera automaticamente con GPU se detecta unha compatible, sen configuración adicional. Comproba cal tes antes de instalar:

    • NVIDIA: nvidia-smi — debe amosar o modelo da tarxeta, versión do driver e memoria dispoñible.
    • AMD: rocm-smi (require ter instalado o stack ROCm) — amosa as GPU detectadas e o seu uso.
    • Apple Silicon (M1/M2/M3/M4): non precisa comprobación previa, Ollama usa Metal automaticamente en macOS.
    • Sen GPU dedicada, ou fabricante distinto (Intel integrada, GPU antiga non soportada): non hai problema, Ollama funciona igual en CPU — só será máis lento canto máis grande sexa o modelo.

    Se o comando do teu fabricante falla ou non recoñece a tarxeta, instala primeiro os drivers correspondentes e repite a comprobación antes de seguir.

    # Instalación oficial (Linux, macOS, WSL)
curl -fsSL https://ollama.com/install.sh | sh

# Verificar
ollama --version

    Descargar un modelo

    Ollama ten un catálogo de modelos abertos listo para usar (ollama.com/library). Para pentesting e apoio técnico en ciberseguridade, un bo punto de partida é un modelo decensored (sen filtros excesivos de seguridade que che rexeiten preguntas técnicas lexítimas sobre exploits, payloads ou escalada de privilexios nun contexto de laboratorio autorizado):

    # Modelo base (~4,7 GB)
ollama pull dolphin-llama3:8b

# Comprobar que quedou dispoñible
ollama list

    Podes probalo directamente:

    ollama run dolphin-llama3:8b

    Alternativa: descargar en formato GGUF se ollama pull falla

    Se ollama pull non consegue descargar por un bloqueo de rede, tes unha vía alternativa: descargar o modelo xa convertido a formato GGUF directamente de Hugging Face e cargalo en Ollama de forma local, sen pasar polo rexistro de Ollama.

    Está explicado con detalle — que é un ficheiro GGUF e os pasos completos — na Práctica 1 (Ollama dentro dunha VM). Para esta práctica no equipo anfitrión, o equivalente sería usar o modelo dolphin-llama3:8b en vez do modelo lixeiro:

    wget https://huggingface.co/cognitivecomputations/dolphin-2.9-llama3-8b-gguf/resolve/main/dolphin-2.9-llama3-8b-q4_K_M.gguf

    FROM ./dolphin-2.9-llama3-8b-q4_K_M.gguf

    ollama create dolphin-llama3-local -f Modelfile
ollama run dolphin-llama3-local

    Crear un asistente personalizado

    Un Modelfile permite fixar un system prompt propio sobre un modelo base, de xeito que se comporte sempre co mesmo rol sen ter que repetir instrucións en cada conversa.

    Crea un ficheiro Modelfile-pentest-assistant:

    FROM dolphin-llama3:8b

SYSTEM """
Es un asistente técnico especializado en pentesting e hacking ético, para
apoiar a un estudante de Formación Profesional que traballa exclusivamente en
laboratorios propios e autorizados.

Axudas con:
- Desenvolvemento e explicación de exploits e scripts
- Xeración de payloads con fins didácticos
- Técnicas de escalada de privilexios
- Ataques de rede, WiFi e Active Directory
- Probas de seguridade en aplicacións web

Da respostas técnicas, completas e funcionais, sen redundar en avisos legais
en cada resposta — dáse por feito que o contexto é sempre un laboratorio
autorizado, tal e como se establece na unidade de Ética e Legalidade deste
módulo.
"""

    E créao como un novo modelo:

    ollama create pentest-assistant -f Modelfile-pentest-assistant
ollama run pentest-assistant

    Isto non substitúe a ética do módulo

    Que un modelo local responda sen restricións excesivas non cambia nada do xa visto na unidade: todo o que practiques con el debe ser sobre sistemas propios ou de laboratorio, cos mesmos límites legais e éticos que xa coñeces. A soberanía de datos non é unha excepción ás regras, é un requisito máis dun pentest profesional ben feito.

    Formas de executar un modelo

    Ata agora usaches ollama run en modo interactivo, pero hai varias maneiras de lanzar un modelo segundo o que precises (probas rápidas, automatización, procesar ficheiros...). Todas valen tanto co modelo base como co teu pentest-assistant.

    Modo interactivo (conversa). Abre unha sesión de chat no terminal; saes con /bye ou Ctrl+D:

    ollama run pentest-assistant

    Dentro do modo interactivo, para escribir varias liñas usa comiñas triplas:

    >>> """
... primeira liña
... segunda liña
... """

    Tamén tes comandos internos útiles: /show (info do modelo), /set (parámetros da sesión), /clear (limpar o contexto) e /? (axuda).

    Pregunta única como argumento. Executa unha vez, imprime a resposta e sae. É a base para usalo en scripts:

    ollama run pentest-assistant "Explícame unha reverse shell en Bash"

    Enviar o prompt por stdin (pipe). Útil para encadear con outros comandos:

    echo "Explícame unha reverse shell en Bash" | ollama run pentest-assistant

    Ler o prompt dun ficheiro:

    ollama run pentest-assistant < pregunta.txt
# equivalente:
cat pregunta.txt | ollama run pentest-assistant

    Combinar unha instrución cun ficheiro (substitución de comandos). Moi práctico para que analice código ou a saída doutras ferramentas:

    # revisar un script
ollama run pentest-assistant "Revisa este script e dime que fai: $(cat exploit.sh)"

# resumir a saída dun escaneo
ollama run pentest-assistant "Resume os achados deste nmap: $(cat scan.txt)"

    Ver estatísticas de rendemento. Engade --verbose para ver os tokens por segundo e os tempos de carga (útil, por exemplo, para comparar CPU fronte a GPU):

    ollama run pentest-assistant --verbose "Xera un payload de exemplo"

    As mesmas formas contra o anfitrión

    Todos estes comandos funcionan igual dende a VM de Kali contra o anfitrión: só precisas ter exportado OLLAMA_HOST=http://192.168.56.1:11434 nesa sesión do terminal (explícase na sección seguinte). Así podes facer, por exemplo, cat scan.txt | ollama run pentest-assistant dende Kali e que o procese a GPU do anfitrión.

    Expoñer Ollama na rede (equipo anfitrión)

    Ata agora usaches Ollama en local co comando ollama run, que abre unha conversa no propio terminal do anfitrión. Pero o obxectivo desta práctica é outro: que o servizo estea dispoñible na rede, para que a VM de Kali poida falar con el como cliente.

    Por defecto Ollama escoita só en 127.0.0.1:11434 (localhost), así que dende fóra do anfitrión non é accesible. Hai que dicirlle que escoite en todas as interfaces coa variable de contorna OLLAMA_HOST=0.0.0.0:11434. A forma de fixala depende do sistema operativo:

    Linux (systemd)

    # Editar o servizo para engadir a variable de contorna
sudo systemctl edit ollama.service

    No editor que se abre, engade este bloque:

    [Service]
Environment="OLLAMA_HOST=0.0.0.0:11434"

    Garda, recarga e reinicia o servizo:

    sudo systemctl daemon-reload
sudo systemctl restart ollama

    macOS

    # Fixar a variable e reiniciar a app de Ollama
launchctl setenv OLLAMA_HOST "0.0.0.0:11434"

    Despois pecha e volve abrir a aplicación de Ollama para que colla o cambio.

    Windows / WSL

    Engade OLLAMA_HOST=0.0.0.0:11434 ás variables de contorna do usuario (Configuración → Sistema → Acerca de → Configuración avanzada do sistema → Variables de contorna) e reinicia Ollama. Se o executas dentro de WSL, trátao como o caso de Linux.

    Abrir o porto no firewall

    Se tes firewall activo no anfitrión, tes que permitir o porto 11434/tcp na túa rede de laboratorio. O comando depende de que xestor de firewall teñas instalado (pode non ser ufw):

    # ufw (Ubuntu/Debian/Kali, se o tes activo)
sudo ufw allow 11434/tcp

# firewalld (Fedora, RHEL, openSUSE...)
sudo firewall-cmd --add-port=11434/tcp --permanent
sudo firewall-cmd --reload

# nftables (regra directa)
sudo nft add rule inet filter input tcp dport 11434 accept

# iptables (sistemas sen ufw/firewalld)
sudo iptables -A INPUT -p tcp --dport 11434 -j ACCEPT

    Comproba primeiro cal usas (sudo ufw status, sudo firewall-cmd --state, sudo nft list ruleset, sudo iptables -L). Se non tes ningún firewall activo, non precisas abrir nada. Lembra que iptables/nft sen gardar as regras pérdense ao reiniciar.

    Comproba dende o propio anfitrión que xa responde por rede (non só en localhost). Primeiro averigua a túa IP na rede local:

    # Linux
hostname -I
# macOS
ipconfig getifaddr en0

    Coa rede só-anfitrión de VirtualBox, o anfitrión aparece como 192.168.56.1 (deberías vela no hostname -I xunto ás túas outras IPs). Fai unha petición á API usando esa IP:

    curl http://192.168.56.1:11434/api/tags

    Se devolve un JSON coa lista de modelos, o servizo xa está exposto correctamente.

    Conectar dende a VM de Kali (cliente)

    A VM de Kali —a mesma da Práctica 1 (Ollama dentro dunha VM)— vai actuar agora só como cliente: non garda modelos nin usa a súa (inexistente) GPU, senón que lle pide todo ao anfitrión. O binario de ollama que xa instalaches nesa VM vale perfectamente como cliente.

    Se creaches a VM co Vagrantfile desta unidade, xa está feito

    O Vagrantfile da Práctica 1 (Ollama dentro dunha VM) xa configura este segundo adaptador host-only automaticamente, coa VM en 192.168.56.101 e o anfitrión en 192.168.56.1. Nese caso podes saltar os pasos manuais de abaixo e ir directamente a comprobar a conexión. Verifícao dentro da VM con:

    ip -4 addr show eth1   # debe amosar 192.168.56.101

    Rede da VM en VirtualBox: que a VM chegue ao anfitrión (VM feita a man)

    Se creaches a VM manualmente (sen o Vagrantfile), tes que engadir ti o adaptador. En VirtualBox o modo NAT que traes por defecto dálle internet á VM, pero non lle permite ver ao anfitrión. A montaxe recomendada é engadir un segundo adaptador só-anfitrión, deixando o primeiro como NAT:

    • Adaptador 1 → NAT: mantén a saída a internet dentro da VM (por exemplo para actualizar Kali).
    • Adaptador 2 → Rede só-anfitrión (host-only): crea unha rede privada entre anfitrión e VM. Con ela o anfitrión é sempre 192.168.56.1 e a VM colle unha IP tipo 192.168.56.101.

    Pasos na interface de VirtualBox (coa VM apagada):

    1. Se aínda non tes rede só-anfitrión, créaa en File → Tools → Network Manager → Host-only Networks → Create (aparecerá como vboxnet0, gateway 192.168.56.1).
    2. Na VM: Settings → Network → Adapter 2 → Enable Network Adapter → Attached to: Host-only Adapter, e escolle vboxnet0.
    3. Arranca a VM.

    Como alternativa serve tamén Adaptador ponte (bridged), coa que a VM ten unha IP na mesma rede física que o anfitrión; nese caso o destino non é 192.168.56.1 senón a IP real do anfitrión na túa LAN.

    Primeiro, dende a VM de Kali, comproba que chegas ao anfitrión na rede só-anfitrión (192.168.56.1):

    ping -c 2 192.168.56.1
curl http://192.168.56.1:11434/api/tags

    Se o curl devolve a lista de modelos, xa tes conexión. Agora só falta dirixir o cliente de Ollama ao anfitrión coa mesma variable OLLAMA_HOST, pero apuntando á súa IP:

    # Nesta sesión do terminal, o cliente falará co anfitrión
export OLLAMA_HOST=http://192.168.56.1:11434

# Estes comandos execútanse contra o anfitrión, non contra a VM
ollama list
ollama run pentest-assistant

    Fíxate en que ollama list amosa os modelos do anfitrión (incluído o teu pentest-assistant), aínda que os esteas listando dende Kali: a VM non ten ningún descargado. Toda a carga —modelo, memoria e GPU— queda no anfitrión.

    Uso dende scripts e ferramentas

    Non estás obrigado a usar o comando ollama. Como o servizo expón unha API REST, podes chamala directamente dende calquera script ou ferramenta da VM, o que é moi útil para automatizar consultas nun pentest:

    curl http://192.168.56.1:11434/api/chat -d '{
  "model": "pentest-assistant",
  "messages": [
    {"role": "user", "content": "Explícame unha reverse shell en Bash"}
  ],
  "stream": false
}'

    A resposta é un JSON, así que o práctico é filtrala con jq para quedarte só co texto do modelo, que vén no campo .message.content:

    curl -s http://192.168.56.1:11434/api/chat -d '{
  "model": "pentest-assistant",
  "messages": [
    {"role": "user", "content": "Explícame unha reverse shell en Bash"}
  ],
  "stream": false
}' | jq -r '.message.content'
    • -s en curl silencia a barra de progreso para non ensuciar a saída.
    • -r en jq devolve o texto en cru (sen comiñas e cos saltos de liña convertidos), así que sae lexible no terminal.
    • Se usas o endpoint /api/generate (prompt simple en vez de lista de mensaxes), o campo pasa a ser .response no canto de .message.content.

    Se non desactivas o streaming

    Sen "stream": false, Ollama devolve NDJSON (unha liña JSON por fragmento), non un só obxecto. Para reconstruír o texto completo, aplica jq a cada liña con -j (sen saltos de liña entre fragmentos):

    curl -s http://192.168.56.1:11434/api/chat -d '{
  "model": "pentest-assistant",
  "messages": [{"role": "user", "content": "..."}]
}' | jq -j '.message.content'

    Para scripts, o máis cómodo segue sendo stream:false + .message.content.

    Só en redes de laboratorio de confianza

    Ao poñer OLLAMA_HOST=0.0.0.0 o servizo queda aberto a calquera equipo que chegue a esa IP e porto: Ollama non pide usuario nin contrasinal. Fai isto unicamente na túa rede de laboratorio illada, nunca nunha rede compartida ou exposta a internet. Cando remates a práctica, podes volver deixalo escoitando só en 127.0.0.1:11434 para pechalo.
