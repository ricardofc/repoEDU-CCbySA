Guía da práctica 1.2 — Desautenticación dun cliente WPA2-PSK

Práctica docente de referencia

Esta guía desenvolve o procedemento do PDF «1-Taller-HE-Practica-WiFi-2.pdf»{:target="_blank"}, centrado na desautenticación dun cliente e na captura do 4-way handshake. É continuación da práctica 1.1 — Auditoría WPA2-PSK.

Uso autorizado

Todos os comandos de inxección de tramas desta práctica deben executarse exclusivamente no escenario virtual psk, coa rede docente EMPRESA-XYZ e as direccións MAC obtidas nesta execución. Non realices estas probas contra redes Wi-Fi alleas.

1. Obxectivos e fundamentos

Nesta práctica comprobaremos como unha trama de desautenticación 802.11 non protexida pode provocar a desconexión dun cliente asociado a un punto de acceso WPA2-PSK sen PMF requirido. Analizaremos o que sucede durante a reconexión e comprobaremos se é posible rexistrar un novo intercambio EAPOL-Key.

A desautenticación non descobre directamente a clave Wi-Fi. Pode provocar unha nova autenticación que facilite a captura dun handshake, sobre o que posteriormente se podería realizar unha proba offline coa ferramenta aircrack-ng e un dicionario. A eficacia desa análise depende da calidade da captura e da fortaleza do contrasinal.

Que é aireplay-ng?

aireplay-ng é unha ferramenta da suite Aircrack-ng que permite inxectar tramas 802.11 mediante unha interface Wi-Fi en modo monitor. Un dos seus usos en auditorías autorizadas é a emisión de tramas de desautenticación para observar a reacción dun cliente.

O PDF de referencia explica a seguinte sintaxe:

sudo aireplay-ng --deauth 10 -a BSSID_AP -c MAC_CLIENTE INTERFACE_MONITOR
  • --deauth 10, equivalente a -0 10: solicita dez ráfagas de desautenticación; non significa necesariamente dez tramas exactas.
  • -a: dirección MAC (BSSID) do punto de acceso.
  • -c: dirección MAC do cliente asociado.
  • INTERFACE_MONITOR: interface desde a que se emiten as tramas.

O programa pode mostrar contadores ACK (confirmacións de recepción a nivel 802.11). Non confundas ACK coa desconexión efectiva: cómpre comprobar tamén o estado do cliente e as tramas capturadas. Un resultado con 0 ACKs tampouco permite, por si só, concluír que a inxección non se transmitiu.

Material necesario

  • Máquina virtual vuln-wifi.lab iniciada, coa sesión gráfica de kali.
  • Escenario psk do laboratorio.
  • Ferramentas iw, airodump-ng, aireplay-ng, tshark e, para a comprobación opcional do contrasinal, aircrack-ng.
  • Dicionario Rockyou, unicamente para a análise offline opcional.

2. Organización das consolas e interfaces

O PDF monta manualmente o punto de acceso e o cliente e emprega catro consolas. Neste laboratorio esas tarefas de preparación xa as realiza wifilabctl; por iso utilizaremos tres terminais abertas no escritorio de Kali, cunha cuarta opcional para observar eventos en tempo real.

| Terminal | Función | Interface empregada | |---|---|---| | Terminal 1 — Preparación e captura | Iniciar o escenario, identificar a rede e capturar paquetes | wlan3 en modo monitor | | Terminal 2 — Desautenticación | Emitir unha proba dirixida ao cliente do laboratorio | wlan2 en modo monitor | | Terminal 3 — Verificación | Consultar a asociación do cliente, os rexistros e analizar a captura | wlan1 no namespace wifi_cliente_wlan1 | | Terminal 4 — Eventos (opcional) | Observar eventos de conexión/desconexión mentres se fai a proba | wlan1 no namespace do cliente |

Interfaces virtuais e namespaces

wlan0 pertence ao AP no namespace wifi_ap_wlan0 e wlan1 ao cliente no namespace wifi_cliente_wlan1. As interfaces globais wlan2 e wlan3 permiten respectivamente a inxección e a captura nesta práctica. Non copies BSSID nin MAC de exemplos anteriores, pois poden cambiar ao reiniciar o escenario.

3. Preparar o escenario (Terminal 1)

Inicia o punto de acceso WPA2-PSK e o cliente:

sudo wifilabctl up psk
sudo wifilabctl status

Identifica a interface do AP, a do cliente e o estado da asociación:

sudo ip netns exec wifi_ap_wlan0 iw dev wlan0 info
sudo ip netns exec wifi_cliente_wlan1 iw dev wlan1 info
sudo ip netns exec wifi_cliente_wlan1 iw dev wlan1 link

Anota nun caderno de prácticas:

  • ESSID esperado: EMPRESA-XYZ.
  • BSSID_AP: dirección MAC do AP que figura na información de conexión do cliente e/ou na observación de rede.
  • MAC_CLIENTE: dirección addr da interface wlan1 indicada por iw dev wlan1 info.
  • Canle esperada: 6.

Se o cliente aparece como Not connected, espera uns segundos e repite a última comprobación. Antes de continuar, confirma a asociación.

4. Recoñecer a rede e iniciar a captura (Terminal 1)

Configura a radio de observación en modo monitor, na canle 6:

sudo ip link set wlan3 down
sudo iw dev wlan3 set type monitor
sudo ip link set wlan3 up
sudo iw dev wlan3 set channel 6
sudo iw dev wlan3 info

Identifica a rede coa ferramenta empregada no PDF:

sudo airodump-ng --channel 6 wlan3

Localiza EMPRESA-XYZ, comproba o seu BSSID e sae premendo Ctrl+C. A continuación inicia a captura específica. Substitúe BSSID_AP polo valor que acabas de comprobar (sen incluír os símbolos < e >):

sudo airodump-ng -c 6 --bssid BSSID_AP -w captura_deauth wlan3

Mantén a Terminal 1 aberta e capturando. O programa creará ficheiros como captura_deauth-01.cap no directorio actual.

5. Observar o cliente antes da proba (Terminal 3)

Abre outra terminal e comproba que segue conectado:

sudo ip netns exec wifi_cliente_wlan1 iw dev wlan1 link

Opcionalmente, se queres observar os eventos de conexión en tempo real, abre a Terminal 4 e deixa executándose:

sudo ip netns exec wifi_cliente_wlan1 iw event -t

Se o evento transitorio non chega a aparecer na terminal, empregaremos igualmente o estado de conexión, os rexistros e a captura para valorar o resultado.

6. Executar unha desautenticación controlada (Terminal 2)

Abre a Terminal 2, mantendo a captura anterior en execución. Configura wlan2 para a inxección:

sudo ip link set wlan2 down
sudo iw dev wlan2 set type monitor
sudo ip link set wlan2 up
sudo iw dev wlan2 set channel 6
sudo iw dev wlan2 info

Emprega só as dúas direccións MAC reais do escenario desta execución:

sudo aireplay-ng --deauth 1 -a BSSID_AP -c MAC_CLIENTE wlan2

Nesta primeira proba enviamos unha única ráfaga para minimizar a interferencia e facilitar a análise. O PDF tamén explica o exemplo --deauth 10; aquí comezamos con 1 e só repetiremos a proba se a evidencia non é suficiente.

Que debemos observar?

  1. Terminal 2: saída de aireplay-ng, incluíndo os ACK comunicados, se os hai.
  2. Terminal 1: novas tramas na captura; se se reproduce a autenticación, airodump-ng pode indicar WPA handshake.
  3. Terminal 3: estado do cliente antes e despois da proba.
  4. Terminal 4 (opcional): eventos relacionados coa desconexión ou reconexión.

Volvemos á Terminal 1 e detemos a captura con Ctrl+C cando xa dispoñamos das evidencias. Non debemos dar por exitoso o ataque unicamente porque aireplay-ng se executase sen erros.

7. Comprobar o resultado (Terminal 3)

7.1. Estado do cliente

sudo ip netns exec wifi_cliente_wlan1 iw dev wlan1 link

Se a asociación se restablece rapidamente, o cliente pode aparecer xa conectado cando consultemos o estado. Por iso é importante revisar tamén os eventos e a captura.

7.2. Tramas de desautenticación na captura

sudo tshark -r captura_deauth-01.cap \
  -Y 'wlan.fc.type_subtype == 0x0c' \
  -T fields -e frame.number -e wlan.sa -e wlan.da \
  -e wlan.fc.protected -e wlan.fixed.reason_code

A presenza de tramas DeAuth con bit protected desactivado documenta a emisión de tramas de xestión non protexidas. Hai que correlacionalas co BSSID e MAC do laboratorio e coa reacción do cliente.

7.3. Mensaxes do 4-way handshake

sudo tshark -r captura_deauth-01.cap -Y eapol \
  -T fields -e frame.number -e wlan.sa -e wlan.da \
  -e wlan_rsna_eapol.keydes.msgnr

Busca as mensaxes M1, M2, M3 e M4; poden aparecer retransmisións ou un intercambio parcial. Se non aparecen, iso non demostra por si mesmo que non houbese desconexión: pode depender do momento da captura e da reconexión.

7.4. Rexistros do cliente (se están dispoñibles)

sudo ls -l /home/kali/wifiLab/run/psk/
sudo grep -Ei 'DISCONNECTED|CONNECTED|EAPOL|4-Way' \
  /home/kali/wifiLab/run/psk/wpa_supplicant.log
Interpretación dos rexistros

Dependendo de como se execute wpa_supplicant, ese ficheiro pode conter pouca información ou só a orde de inicio. A ausencia de eventos nel non invalida automaticamente a proba: contrasta os datos co PCAP e co estado real da interface.

8. Análise offline opcional con Rockyou

O PDF de referencia remata cunha proba de dicionario sobre o handshake capturado. Esta fase non é imprescindible para demostrar a desautenticación; permite estudar a relación entre reconexión, captura EAPOL e robustez do contrasinal WPA2-PSK.

Se existe o dicionario comprimido e aínda non está descomprimido:

sudo gzip -dk /usr/share/wordlists/rockyou.txt.gz

Se rockyou.txt xa existe, omite o paso anterior. Analiza exclusivamente a captura do escenario:

sudo aircrack-ng -w /usr/share/wordlists/rockyou.txt captura_deauth-01.cap

No PDF amósase o resultado de exemplo KEY FOUND! [ spongebob19 ]. Non é unha saída garantida: require unha captura adecuada e que a frase de paso figure no dicionario. Esta análise non transmite novos paquetes contra o AP.

9. Evidencias que debe recoller o alumnado

  1. Captura ou anotación do ESSID, BSSID do AP, MAC do cliente e canle.
  2. Estado da asociación antes e despois da desautenticación.
  3. Orde aireplay-ng empregada e saída real, sen interpretar os ACK como proba definitiva.
  4. Tramas DeAuth identificadas en captura_deauth-01.cap, indicando se estaban protexidas.
  5. Mensaxes EAPOL observadas, se houbo unha nova autenticación.
  6. Resultado da análise offline, só se se realizou.

Criterio de validación: considérase demostrada a desautenticación cando a evidencia permite relacionar a inxección dunha trama DeAuth non protexida cunha desconexión ou reasociación real do cliente. Un handshake novo constitúe unha evidencia adicional, non un requisito para concluír que existiu a desconexión.

Se só observamos a emisión de tramas sen ningún cambio demostrable na asociación, o resultado debe rexistrarse como non concluínte, non como ataque exitoso.

10. Limpeza e seguinte práctica

Cando termines, detén as ferramentas de captura e observación abertas e restaura o laboratorio:

sudo wifilabctl reset

Na práctica 1.3 — Protección das tramas de xestión (PMF) compararemos esta situación cun cliente que negocia PMF requirido. As tramas de desautenticación falsificadas e non protexidas deberían ser rexeitadas tras establecerse esa protección.
